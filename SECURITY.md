# Безопасность и обслуживание

Дата проверки: **16 ноября 2026 года**. Область: исходный код бота, HTTP webhook,
обработка расписаний PDF/XLSX, статистика, служебные скрипты и зависимости.
Проверка проводилась локально; это не внешний пентест инфраструктуры Telegram,
Vercel, Google или Upstash и не нагрузочное испытание production.

## Данные и модель доступа

Расписания университета и агрегированные счётчики пользователей доступны публично
по выбранной владельцем модели. Такое поведение не считается уязвимостью.
Действующие ограничения через `ADMIN_USER_IDS` сохранены. В проекте нет доступа
к личным оценкам или университетским учётным записям.

Хранилище статистики содержит Telegram `user_id` и отметки активности; публичный
ответ `/stats` содержит агрегаты. Доступ к самой БД и её учётным данным должен
оставаться у владельца. Секреты Telegram, webhook и Redis — отдельные доверенные
данные окружения, а загружаемые документы и входящие сообщения проходят проверку.

## Что не подтвердилось

- **SQL-инъекция не обнаружена:** изменяемые значения передаются в SQLite
  параметрами, а не вставляются в SQL. Дополнительно введена строгая проверка ID
  до обращения к хранилищу; строки, `bool` и значения вне диапазона отклоняются.
- **Lua-инъекция не обнаружена:** код Redis-скриптов постоянный, ключи и значения
  передаются отдельно через `KEYS`/`ARGV`. Тесты проверяют попытки подмены ID и ключей.
- HTML из поиска и расписаний экранируется при формировании сообщений Telegram;
  это подтверждено регрессионными проверками.

[tests/test_security_application.py](tests/test_security_application.py).

## Проверки и границы результатов

- **481 тест пройден** в чистом Python 3.12 окружении: 215 исходных сценариев
  и 266 дополнительных проверок безопасности и регрессий. Реальный XLSX после
  финальных ограничений дал 507 записей на 17 дат; все 158 найденных групп
  сохраняют выдачу недельного расписания одним PNG.
- Локальные тесты проводят реальные HTTP-запросы к `ThreadingHTTPServer`, далее
  через настоящий webhook и `python-telegram-bot Application` к обработчикам.
  Telegram заменён тестовым `BaseRequest`; внешние загрузки и хранилища подменены.
  Проверены существующие команды, кнопки, анонимные администраторы групп,
  ошибочные HTTP/JSON-запросы, лимиты ресурсов и попытки инъекций.
- Bandit: **0 замечаний** в проверенном runtime-коде `app`, `api`, `scripts`.
- Аудит зафиксированного runtime-набора: **17 пакетов, 0 известных advisories**
  на момент проверки. Это не доказывает отсутствие неизвестных уязвимостей.
- Поиск секретов по шаблонам в истории: **27 коммитов, 106 blob-объектов,
  0 кандидатов** в проверенном наборе. Он не покрывает журналы Vercel, секреты
  провайдеров, игнорируемые/неотслеживаемые файлы и все возможные форматы секретов.
  Такой результат не отменяет подтверждённое прежнее появление токена в журнале.
- Наличие CI-файла не означает, что удалённый запуск GitHub Actions уже прошёл:
  его результат нужно проверить после публикации соответствующего коммита.

## Остаточные риски

1. Лимиты запросов и кэш повторных `update_id` действуют **в одном процессе**.
   Новый экземпляр Vercel начинает со свежего состояния; распределённой защиты
   от повторов и глобального ограничения нагрузки нет. Кэш хранит до 4096 ID
   на срок до 24 часов; старые записи могут быть вытеснены раньше.
2. PDFium — нативный парсер, работающий в процессе бота **без отдельной песочницы**.
   Ограничения размера и количества объектов снижают риск, но не заменяют
   изоляцию и обновления библиотеки при появлении исправлений.
3. `asyncio`-тайм-аут прекращает ожидание, но не гарантирует остановку уже
   выполняющегося потока, сетевой операции или нативного парсера. Сетевые тайм-ауты
   и проверки срока загрузки также не являются принудительным завершением процесса.
4. Адреса Redis и webhook задаёт оператор. Проверки URL не подтверждают владение
   доменом и не исключают изменение DNS; конфигурация, DNS и доступ к аккаунтам
   хостинга остаются доверенной границей.
5. Сбои или изменения официального сайта/Google, Telegram и Upstash могут нарушить
   доступность. Ограничения парсера могут отклонить новый корректный формат —
   в таком случае следует исследовать документ, а не просто повышать все лимиты.
6. Постоянный учёт уникальных пользователей хранит ID и активность без автоматического
   срока удаления. Владельцу нужно учитывать доступ к БД, резервным копиям и срок
   хранения при изменении политики статистики.

## Порядок обслуживания для владельца

1. Хранить `TELEGRAM_BOT_TOKEN`, `WEBHOOK_SECRET` и Redis-токен только в секретах
   нужного окружения хостинга; не отправлять их в чат, issue, скриншоты или Git.
   Для Vercel проверить окружение **Production**. В качестве `WEBHOOK_SECRET`
   выбрать случайное значение высокой энтропии из `A-Z`, `a-z`, `0-9`, `_`, `-`
   длиной 1–256 символов; рекомендовано не менее 32 случайных байт в URL-safe форме.
2. После изменения секрета выполнить redeploy и установить webhook тем же значением
   в локальном окружении: `python -m scripts.set_webhook https://your-domain.vercel.app`.
   Скрипт сохраняет ожидающие обновления (`drop_pending_updates=False`). Проверить
   ответы `/start`, `/stats`, `/group` и состояние доставки через безопасный вывод
   скрипта. Не размещать секрет в URL webhook.
3. **Рекомендуется перевыпустить прежний токен через BotFather:** он ранее был виден
   в INFO-журналах HTTPX до подавления такого логирования. Затем обновить секрет
   Telegram на хостинге и в защищённом локальном окружении, выполнить redeploy,
   повторно зарегистрировать webhook и проверить команды. Факт появления в журнале
   не доказывает, что токен был получен или использован посторонним. Маскирование
   новых логов не удаляет старые записи; ограничить к ним доступ и удалить доступные
   копии согласно возможностям провайдера.
4. Устанавливать runtime с проверкой хешей:
   `python -m pip install --require-hashes --only-binary=:all: -r requirements.txt`.
   Обновлять версии намеренно через `requirements.in`, заново генерировать lock
   с хешами и проверять diff. После обновления повторять тесты и аудит; не удалять
   проверку хешей, чтобы обойти ошибку установки.
5. Проверять GitHub Actions после каждого изменения: `pip check`, `pytest`,
   `compileall`, Bandit и `pip_audit` описаны в
   [.github/workflows/security.yml](.github/workflows/security.yml).
   Следить за 5xx webhook, повторной доставкой, ростом расходов/запросов и ошибками
   источников расписания. При расследовании сохранять время, тип ошибки и ID
   deployment, предварительно очищая журналы от секретов.

Сообщая о проблеме, передавать владельцу приватно путь обработчика, условия
воспроизведения и обезличенный пример. Действующие токены и пользовательские данные
не включать в публичные отчёты.
